### Fase 1 — Issue #4: WRITE_SECURE_SETTINGS persistente (15 min)
**Por qué primero**: si el permiso se pierde, todas las otras fixes fallan con crash.

- [ ] En `adb_tablet --setup`, después de `pm grant`, **verificar** que `granted=true`. Si no, reintentar 3 veces.
- [ ] En `MiroLauncherActivity.onCreate`, **antes de intentar el toggle**, verificar `checkCallingOrSelfPermission(WRITE_SECURE_SETTINGS)`. Si falta, log warning y mostrar UI "permite el permiso".
- [ ] Agregar un `BootReceiver` o un `Application.onCreate` que re-grant-ea el permission si está en false. **No se puede re-grantear desde la app misma** (es chicken-and-egg), pero **se puede pedirle al user via intent** `ACTION_MANAGE_APPLICATION_DETAILS_SETTINGS`.

### Fase 2 — Issue #1: pantalla oscura launcher (30 min)
**Por qué segundo**: este es el root cause de varios problemas downstream.

- [ ] **Cambiar theme** a `Theme.NoDisplay`:

- [ ] **Test**: `am start -n com.miro.a11y/.MiroLauncherActivity` + verificar con `uiautomator dump` que la activity no se queda visible.

- [ ] Si ninguno funciona, **abandonar el patrón HOME wrapper** y probar:

  - `Intent.ACTION_LOCKED_BOOT_COMPLETED` (nunca probado)
  - `BootReceiver` con `directBootAware="true"`

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| `Theme.NoDisplay` rompe el flow HOME | Mantener `Theme.Translucent.NoTitleBar` como fallback |
| OLAX bloquea `ACTION_LOCKED_BOOT_COMPLETED` | Aceptar: seguir con HOME wrapper + workaround manual |
| El bounds-parser del dialog falla | Hardcode fallback a (721, 372) |
| `getRecentTasks()` está deprecated en API 31+ | Usar `ActivityManager.getRecentTasks(maxNum, RECENT_WITH_EXCLUDED)` con try-catch |
| El user pierde connectivity al wireless | Mantener `adb_wifi_enabled` path, no tocar |
